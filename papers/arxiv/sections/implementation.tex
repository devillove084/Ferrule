\section{Implementation}
\label{sec:implementation}

\subsection{Private model-operator path}
\label{sec:implemented-read-path}
The evaluated Mixed-precision model path implements Algorithm~\ref{alg:bounded-lookahead}
inside its private CUDA expert operator. It does not instantiate the general
runtime resource manager or materialization registry for these expert reads.
Its local owners implement source validation, host quota, device-cache
admission, and consumer completion. Algorithms~\ref{alg:normal-materialization}
and~\ref{alg:terminal-custody} provide reference contracts for reasoning about
these responsibilities, not a claim of one universal call path.

The checkpoint catalog records tensor descriptors and ordered file extents.
A read plan binds filesystem identity using device, inode, length, modification
time, and change time. The worker verifies this identity before and after
positioned reads; the consumer rechecks it before constructing the three
compressed gate, up, and down artifacts. Descriptor hashes describe dtype,
shape, and extent metadata rather than authenticating every payload byte.
The worker receives neither CUDA handles nor cache leases or runtime
continuations.

Both schedules explicitly enable this worker. Blocking submits required
demand and waits; lookahead carries one exact next ticket across current
compute submission. After upload, the operator computes from resident device
handles and immutable binding metadata, allowing temporary host aliases to
retire before the next read. Kernel mathematics, selected expert order, and
completed-only cache replacement remain unchanged. A pipeline-disabled path
would not be an equivalent control.

The principal configuration uses a 64 MiB host limit containing 8 MiB of
metadata and 2 MiB of requested stack reservation. The remaining 54 MiB is
split equally between packed and prepared payload quota. Device cache and
scratch are separately accounted. Prepared payload charges survive escaped
weight or scale aliases. Passive snapshots report mode, read counts, waits,
payload charges, join state, and retained uncertainty without changing them.
Allocator detail is omitted from passive snapshots when obtaining it would
poll retirement fences.

\subsection{Other protocol implementations}
The general materialization path installs a registry only when a runner
transfers a physical provider to the resident engine. This path merges
compatible exact keys, validates completion before mutation, and separates
stage-custody return from credit release and resident-grant transfer. Its
routed-expert provider uses pinned host reads and CUDA upload and installation.
Registered slabs retain aligned ranges and generations; upload tickets retain
the original event and frame after notification errors. Replacement also
carries the old binding and its consumer-completion evidence.

The resource broker canonicalizes and checks claims before charging them.
A later-stage budget wait retains earlier buffers and destinations. Grants
have no implicit destructor refund. The five accounting classes in
Equation~\ref{eq:credit-conservation} are refinements of these ownership
states, not five directly measured counters.

State publication uses a separate prepared-state protocol. A provisional
journal precedes backend preparation because preparation can submit work
before returning a handle. Lost installation acknowledgments cause polling
of the same operation rather than redispatch. Exact acknowledgments precede
logical publication; displaced-state retirement and page confirmation precede
reuse. Committed KV reads revalidate owner, slot, incarnation, generation,
layout, frontier, range, and page authority. Finishing a transaction consumes
its handle custody, not every independent weight, KV page, or cache pin.

These integrations share ownership concepts but have different progress and
completion authorities. An exact late registry completion may close its
stage while an independent device owner remains poisoned. Host-worker join
cannot clear that device uncertainty. Ordinary pipeline, host-KV, and
collective paths therefore require their own audits; the evaluated
single-device path does not establish universal registry coverage or a
default device-collective implementation.
